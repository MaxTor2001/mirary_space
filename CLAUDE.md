# Mirari — заметки для работы в репозитории

Монолит Django (API, порт 8000) + витрина Node.js/Express+EJS (порт 3000) + PostgreSQL. Описание
структуры и API — в `README.md`, здесь только рабочие правила и подводные камни.

## Рабочий цикл

- Всё запускается через `docker compose up -d --build`; после правок бэкенда достаточно
  `docker compose restart backend`, миграции и `seed_demo` выполняет `backend/entrypoint.sh`.
- Python-команды локально — только через `uv run` из `backend/` (`uv run manage.py ...`), зависимости — `uv add`.
- Новые модели: `uv run manage.py makemigrations` локально (подключение к БД не требуется), миграции коммитим.

## Прод

- Сайт: https://mirari.space на сервере `45.89.229.24` (ssh-алиас `fstek`), каталог `/home/deploy/mirari`.
- Выкатка: `git push origin main`, затем `ssh fstek '/home/deploy/mirari/deploy/deploy.sh'`
  (fetch + `reset --hard origin/main` + пересборка). Откат — `git reset --hard <хеш>` и та же пересборка.
- `sudo` на сервере под паролем и пользователь его не даёт: команды для nginx и certbot отдаём ему
  готовыми, сами не выполняем. Планировать работу так, чтобы root требовался как можно реже.
- На сервере рядом живёт чужой проект `fstek239-web` (theartfstek.online, порт 8001, свой vhost).
  Ломать нельзя; после работ проверять `md5sum /etc/nginx/sites-available/fstek239.conf` и что сайт отдаёт 200.
- Прод-настройки — в `docker-compose.prod.yml` (только отличия от базового файла). На сервере в `.env`
  задан `COMPOSE_FILE=...:docker-compose.prod.yml`, поэтому там работает голое `docker compose up -d --build`.
- Админка не на `/admin/`: путь задан `DJANGO_ADMIN_PATH` в `.env`, тот же путь прописан в `location` nginx.
- Демо-каталог на проде выключен (`SEED_DEMO=0`); включать обратно нельзя — сид пересоздаст удалённые товары.

## Подводные камни

- `postgres:18` хранит данные в `/var/lib/postgresql`, а не в `/var/lib/postgresql/data`. Том смонтирован
  на `/var/lib/postgresql`; менять обратно нельзя — контейнер БД падает на старте.
- Витрина не имеет своей БД: любые новые данные на странице сначала появляются как эндпоинт DRF,
  затем как вызов `api()` в `frontend/src/routes/*.js`.
- Корзина гостя опознаётся заголовком `X-Cart-Session`; при добавлении нового эндпоинта корзины
  используйте `carts/services.py: cart_owner()`, а не обращение к `request.user` напрямую.
- Новую переменную окружения мало положить в `.env` — её надо объявить в `environment:` нужного сервиса
  в `docker-compose.yml`, иначе она молча не дойдёт до контейнера — частая и незаметная ошибка.
  После добавления проверять: `docker exec <контейнер> printenv | grep ИМЯ`.
- Адреса файлов для браузера строим из `PUBLIC_MEDIA_URL`, а не из запроса: витрина ходит в API по
  внутреннему имени `backend:8000`, и построенный от запроса адрес браузер не откроет.
- Картинки товаров лежат в каталоге на хосте (`MEDIA_DIR`) и отдаются nginx; `Product.save()` ужимает
  оригинал до 1600 px и делает миниатюру 480 px, при замене фото удаляет прежние файлы — Django сам их не трогает.
- Поля вроде `is_staff` в `UserSerializer` держим `read_only`: тем же сериализатором обновляется профиль,
  иначе покупатель выпишет себе права запросом `PATCH /api/users/profile/`.
